# 0006. Ролі — у `profiles`, «без ролі» — `null`, admin-клієнта в застосунку немає

- Статус: прийнято
- Дата: 2026-10-26
- AC: AC-CARD-06, AC-CARD-07, AC-CARD-10, AC-CARD-11

## Контекст

Зріз 2 — перший зріз із правами «хто НЕ може»: картки створюють лише admin і scheduler (AC-CARD-06), відвідувач без
входу бачить лише сторінку входу (AC-CARD-07), а користувач, який увійшов, але ролі не має, — лише повідомлення
«Your account has no access yet. Contact an administrator.» (AC-CARD-11). Матриця прав `requirements/product.md`: роль
призначає лише адміністратор, підвищити роль сам собі не може ніхто; у WS6–WS7 ролі — лише початкові дані (сид),
керування ролями й запрошень у застосунку немає. Server Action — публічний POST, а публічний ключ — у бандлі, тож
перевірка лише в proxy чи на сторінці нічого не захищає.

## Рішення

- **Роль — колонка `profiles.role`**, джерело правди для RLS (`private.has_role`) і для коду (`requireRole`). Ніколи з
  `user_metadata` чи JWT. Змінити роль може лише `service_role` (скрипт сиду): `grant update` для користувача — лише на
  `full_name`.
- **«Без ролі» — `role is null`:** міграція `client_cards` у порядку drop-first знімає `profiles_role_check`, дозволяє
  `null` і ставить `default null`, тож новий користувач Auth отримує профіль без ролі. `private.has_role(null)` дає
  `false` — користувач без ролі не проходить жодної політики.
- **Одне рішення на вході — `accessFor`** (`src/lib/auth/access.ts`), яке викликає `requireRole` на початку кожної
  сторінки й дії: без входу → `/login`, без ролі → `/no-access`, роль не з дозволених → `/`. Proxy лише перенаправляє
  (UX).
- **Admin-клієнта (`SUPABASE_SECRET_KEY`) у застосунку немає:** ролі ставить `npm run users:demo` локально, запрошень
  немає. Ключа немає у Vercel, а в `src/` його читав би лише `src/lib/supabase/admin.ts` (файлу немає).

## Розглянуті варіанти

- **Роль у JWT (Custom Access Token Hook)** — ні: роль у токені застаріває до його оновлення (зняту роль ще годину
  бачили б RLS і сторінки), потрібен ще один хук у налаштуваннях проєкту, а курс прямо забороняє роль з
  `user_metadata`.
- **Окреме значення ролі `pending` замість `null`** — ні: «без ролі» у PM — відсутність ролі; `null` уже не проходить
  `has_role` без змін у політиках, а ще одне значення довелося б додавати в кожну перевірку й `profiles_role_check`.
- **Admin-клієнт у Server Action для ролей і карток** — ні: у зрізі немає керування ролями, а admin-клієнт обходить RLS —
  помилка в перевірці ролі відкрила б усі картки. Запис картки йде клієнтом користувача, тож RLS відмовляє й на прямий
  запит.

## Наслідки

- Керування ролями в застосунку (пізніше за roadmap) — окрема функція бази в `private` з перевіркою ролі й захистом
  останнього адміністратора, а не admin-клієнт; тоді — новий ADR.
- Новий екран або дія починається з `requireRole`; `/no-access` — виняток (перевіряє лише вхід, інакше цикл).
