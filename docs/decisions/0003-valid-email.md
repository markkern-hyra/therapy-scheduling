# 0003. «Valid email» клієнта — check-обмеження в базі

- Статус: прийнято
- Дата: 2026-10-21
- AC: AC-HOLD-11, AC-HOLD-15, AC-HOLD-16, AC-HOLD-34, AC-HOLD-35

## Контекст

PM вимагає «коректний email» (AC-HOLD-15: email без @ відхиляється), але правила формату не визначила — це припущення
розробника в зміні `add-slot-hold`. Email має бути унікальним без урахування регістру й пробілів на початку й у кінці
(AC-HOLD-34) і зберігатися малими літерами без цих пробілів (AC-HOLD-35). Принцип `design.md`: правило запису живе в
одному місці — у базі, щоб прямий запит до Data API отримав ту саму відмову, що й форма.

## Рішення

- Колонка `clients.email` — `not null`, `unique` (`clients_email_key`) і check `clients_email_check`:
  `email = lower(btrim(email))` і `email ~ '^[^[:space:]@]+@[^[:space:]@]+\.[^[:space:]@]+$'` — рівно один `@`,
  непорожні частини до й після нього, у домені є крапка, без пробілів.
- Форма лише нормалізує email перед записом (`clientFromForm` у `src/lib/scheduling/clients.ts`: `trim` і нижній
  регістр); формат не перевіряє.
- Порушення check (`23514`) → код `CLIENT_INVALID` → «Enter the client's name and a valid email.»; порушення unique
  (`23505`) → `CLIENT_EXISTS` → «A client with this email already exists.» (`src/lib/scheduling/messages.ts`).
- Ім'я — check `clients_full_name_check`: `full_name ~ '[^[:space:]]'` (хоча б один непробільний символ; `btrim` знімає
  лише пробіли, а не табуляцію й переноси), той самий код `CLIENT_INVALID`.

## Розглянуті варіанти

- Перевірка формату в TypeScript (регулярний вираз або `type="email"` браузера) — ні: друге джерело правила, прямий
  запит до Data API його обходить, а підказка браузера — не текст PM. Тому форма має `noValidate`.
- Повна граматика RFC 5322 — ні: складно, а AC вимагають лише відхилити email без `@`.
- Тип `citext` для регістронезалежної унікальності — ні: зберігання вже нормалізованого email простіше й одразу дає
  AC-HOLD-35.

## Наслідки

- Прямий запис ненормалізованого email (` Client1@Example.TEST `) через Data API відхиляється як `CLIENT_INVALID`, а не
  нормалізується — нормалізує лише форма застосунку.
- Якщо PM уточнить формат, змінюємо лише `clients_email_check` новою міграцією (і цей ADR — статусом «замінено»).
